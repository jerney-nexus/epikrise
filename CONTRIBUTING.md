# Contributing

Thanks for your interest. This document covers the development setup, the project layout and the rules that keep the codebase safe for clinical use.

## Ground rules

Epikrise handles clinical text. Two constraints override normal convenience:

1. **Clinical content must never be persisted or logged.** Temporary OCR image files may be written only to private temporary directories; overwrite them before removal and clean up abandoned directories on the next launch. Never include clinical content in debug output or error messages.
2. **No panicking code paths.** `unwrap`, `expect`, `panic!` and friends are denied by clippy outside of tests. Return a typed error instead.

Both rules are enforced mechanically; see [Quality gates](#quality-gates).

## Development setup

Use the [dev container](.devcontainer/devcontainer.json), which has everything preinstalled. For a native setup, follow the [Development setup](https://github.com/jerney-nexus/epikrise/wiki/Development-Setup) wiki page for your operating system, including OCR language data. Toolchain versions are in the [README requirements](README.md#requirements), and the first commands are in [Getting started](README.md#getting-started).

## Project layout

```
.devcontainer/            dev container definition and setup scripts
.github/                  workflows, issue templates, and the PR template
docs/                     project website (SvelteKit, prerendered) and privacy policies, published with GitHub Pages
locales/                  Fluent message catalogs, one folder per language
scripts/                  build, packaging, OCR, and release helpers
src/                      SvelteKit frontend (SPA, no SSR); bindings.ts is generated
src-tauri/                Tauri application: commands and wiring only
  crates/                 epikrise-core, epikrise-ingest, epikrise-llm
  capabilities/           Tauri permission capabilities
  icons/                  application and Store icons
  msix/                   Store MSIX manifest
static/                   static files copied as-is into the frontend build
store-assets/             Microsoft Store listing images and metadata
tests/                    Vitest unit and tooling tests; Playwright specs in tests/e2e/
templates/, fixtures/clinical/   git-ignored local clinical material
```

The three library crates deliberately have no Tauri dependency. Business logic belongs there, not in `src-tauri/src/`, so it can be unit-tested without spinning up a webview. `src/bindings.ts` is generated by Tauri Specta; do not edit it by hand.

For each module and its role, see [Project Layout](https://github.com/jerney-nexus/epikrise/wiki/Project-Layout).

## Quality gates

Before opening a pull request, run at least:

```sh
pnpm check
pnpm test
pnpm build
```

The full gate list, including formatting, linting, and audit commands, is on the [Testing wiki page](https://github.com/jerney-nexus/epikrise/wiki/Testing).

## Commits and changelog

Use Conventional Commit subjects (`feat: add template importer`, `fix: handle formatted output`) and keep each commit focused on one change. User-visible changes get an entry under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md).

Release preparation, the release gates, and the updater and Store rules are documented in the [Releasing](https://github.com/jerney-nexus/epikrise/wiki/Releasing) wiki page.

## Pull requests

Use the generic pull request template for regular changes. Release pull requests use the release-specific template and generated Store release-notes checklist. Store metadata refresh pull requests are opened with a dedicated review body; review the full metadata diff and resolve base-only changes, especially unreleased release notes, before merging.

See [ACCESSIBILITY.md](ACCESSIBILITY.md) for accessibility expectations and checks.

## Project website

The public website is a standalone SvelteKit app in `docs/`, prerendered to static HTML with `@sveltejs/adapter-static` by [vite.site.config.js](vite.site.config.js). Pages live in `docs/src/routes/` (the index and `privacy-policy/[lang]/`). The Markdown sources are in `docs/src/lib/content/` and are rendered at build time by `docs/src/lib/server/`; shared header, footer, and theme controls are in `docs/src/lib/components/`, and styles in `docs/src/lib/styles/`. Static files in `docs/static/` (including `CNAME` and `favicon.png`) are copied as-is. [pages.yml](.github/workflows/pages.yml) runs `pnpm site:build` and deploys `build/site` with GitHub Pages on pushes to `main`. The Pages source is GitHub Actions, so keep it set to that rather than to a branch folder. To preview locally, run `pnpm site:dev` and open the printed URL; use `pnpm site:build` to produce `build/site`.

## Localization

User-facing strings live in Fluent catalogs under `locales/`. Rust code returns translation keys and arguments, never localized text — the frontend resolves them. Adding a language means adding a folder; do not hardcode strings in command return paths.

English literals that are intentionally not translated are not hardcoded UI strings and should not be flagged in review:

- Brand and provider names, such as Epikrise, Ollama, OpenAI, Anthropic, Gemini, OpenRouter, Groq, and xAI.
- Text sent to the model, such as the correction prompt built in `regenerateWithCorrections` in `src/routes/+page.svelte`.
- Persisted template data, such as the default section heading and `labels` written by `addTemplateEditorSection`. Stored data must not follow the UI language.
- Fluent source strings passed to `t()` or assigned to status state, such as `generationMessage = "Draft ready"`. `t()` resolves them through the catalogs, and missing keys fall back to the English source, so keys must be added to every catalog.
- CSS font names and placeholder URL examples.

Startup dialogs, the window title, and the Crowdin translation review are described in the [Localization wiki page](https://github.com/jerney-nexus/epikrise/wiki/Localization).

## Templates and test data

Never commit real or realistic clinical material, not even as a test fixture. The `templates/` and `fixtures/clinical/` directories are git-ignored for this reason. Fixtures used by tests must be synthetic.

## Reporting security issues

Report vulnerabilities privately as described in [SECURITY.md](SECURITY.md). Do not open a public issue, especially for anything that could expose clinical content.
